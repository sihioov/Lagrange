작성일: 2026-10-26 (Asia/Seoul). 상태: **DRAFT — 새 계산 규칙의 Owner 결정 전**.
제안 버전: `owner-beta-price-only-simulation-v2-draft-1`.
소스 기준: `d100c81f31dcd4495271e4318a82d28f6cb74aff`.

R4-05 구현·격리 검증 완료 뒤 Owner가 “이어서 진행해”라고 지시해
[R4-06](../../ROADMAP.md)의 다음 범위를 조사했다. 이 문서는 구현과 검증의 구체적인 입력이며,
아직 새 규칙으로 성과를 계산하거나 운영에 설치한 기록은 아니다.

## 검토할 권장안

기존 추천에 있는 다섯 전략의 **기본 설정**을 같은 기간·같은 초기자금·같은 비용으로 비교한다.
기존 추천 팩터와 목표 비중 계산을 재사용한다. 매수 후 보유는 처음 한 번,
50/200 추세 전략은 신호 전환 때, 나머지 세 전략은 월말 신호 다음 거래일에 매매한다.
여러 종목에 나눠 투자할 때는 정수 주를 사용하고, 비용까지 포함한 매수 예산이 부족하면
종목별 필요 예산에 비례해 줄인다. 남은 돈은 다음 재조정까지 현금으로 둔다.

다음 여섯 항목을 하나의 버전으로 결정하는 것을 권장한다.

| 항목 | 권장 규칙 | 결과에 미치는 영향 |
| --- | --- | --- |
| 대상 | 기존 다섯 전략의 아래 고정 기본 설정만 제공 | 임의 설정·새 전략의 검증 범위를 제한 |
| 비교 기간 | 다섯 전략의 실제 팩터 준비가 모두 끝난 첫 공통 거래일부터 같은 종료일까지 | 짧은 준비 기간의 전략도 같은 기간으로 비교; 기존 v1 전체 기간 결과와 구별 |
| 매매 일정 | 최초 공통일 진입, 이후 전략별 전환/월말 일정 | 월별 전략을 매일 재조정해서 성과·비용을 바꾸지 않음 |
| 수량·현금 | 목표 수량 내림, 순매도 후 매수, 부족 예산 비례 배분, 잔액 현금 | 비용·정수 주 때문에 실제 비중은 목표와 다를 수 있음 |
| 비교 기준 | 기존 069500 매수 후 보유와 두 비용 프로필 유지 | 비용이나 벤치마크 변경 없이 전략 차이를 비교 |
| 호환성 | v1 결과·계약·해시는 보존하고 v2를 별도 식별 | 이전 성과를 새 규칙으로 해석하거나 덮어쓰지 않음 |

## 1. 그대로 유지하는 승인 경계

원본 [v1 계약](2026-10-23-r4-price-only-simulation-contract-draft.md)과
[Owner 결정 기록](../../handoffs/2026-10-23-r2-r3-to-r4.md)은 수정하지 않는다.
v1은 069500 단일 보유·현금 전환과 200종가 준비 기간을 전제로 이미 검증됐다.
그 계약의 해시 아래 다종목·월별 재조정 결과를 새로 넣지 않는다.

- 같은 승인 v3 ETF11 입력과 정확한 다섯 pin을 사용한다. 기간 밖 데이터·새 provider는 추가하지 않는다.
- `OWNER_ONLY`, `PRICE_RETURN_ONLY`, `vendor_snapshot=true`, `strict_pit=false`를 유지한다.
- 초기자금 `10000000.0000` KRW, 정수 주, 차입·공매도·현금 이자·입출금 없음.
- T 종가까지의 adjusted close로 신호를 계산하고 다음 승인 세션의 raw open에 체결한다.
- raw close로 평가한다. raw/adjusted OHLC 수치 일치와 비현금 action 0 조건은 유지한다.
- 필요한 가격·세션·종목 누락은 전체 실패다. 보간·전일값 대체·우주의 축소는 하지 않는다.
- 비용은 양쪽 각각 거래 원금의 1/1000을 0.0001원 단위로 올림하는 가정과 0비용을 별도 실행한다.
  실제 수수료·세금·슬리피지 추정이라는 주장은 하지 않는다.
- 배당 포함 총수익, 연환산 수익률, Sharpe, 엄격한 PIT 성과를 추가하지 않는다.

## 2. 고정 전략과 기존 추천 계산

출처는 [baseline registry](../../../crates/selector/src/baseline.rs)와
[Owner-beta 목표 계산](../../../crates/job-queue/src/owner_beta/target.rs)이다.
모든 전략 버전은 `1.0.0`이며, 아래 설정의 canonical snapshot을 결과와 요청 identity에 묶는다.

| 전략 | 허용 기본 설정 | 팩터 | v2 매매 일정 |
| --- | --- | --- | --- |
| `buy_and_hold` | `benchmark_instrument=069500.KRX`, `target_weight=1.0`, `rebalance_cadence=none` | 없음 | 공통 시작일 최초 매수 후 보유 |
| `trend_following` | `benchmark_instrument=069500.KRX`, `fast_ma=50`, `slow_ma=200` | `trend_50`, `trend_200` | 매일 신호 확인, 0%↔100% 전환 때만 체결 |
| `relative_momentum` | `top_n=3`, `lookback_months=12` | `momentum_12_1` | 최초 진입 후 월말 재조정 |
| `dual_momentum` | `absolute_threshold=0.0`, `lookback_months=12` | `return_12m` | 최초 진입 후 월말 재조정 |
| `inverse_volatility` | `vol_window=60`, `max_weight=0.3` | `vol_60` | 최초 진입 후 월말 재조정 |

기존 팩터와 target snapshot을 호출하며 새 수식으로 복제하지 않는다.
추천 결과의 동률·반올림·현금 잔여 규칙도 그대로 따른다. 특히 다음 차이는 의도적으로 보존한다.

- 추세는 `close/SMA-1` 표현 때문에 `trend_50 < trend_200`일 때 투자한다. 동률은 현금이다.
- 상대 모멘텀은 값 내림차순·동률 종목 ID 오름차순으로 순위를 정한다.
- 듀얼 모멘텀은 동일 최고값일 때 종목 ID가 큰 항목을 고르고, 수익률이 0보다 클 때만 투자한다.
- 상대 모멘텀의 1/3은 기존 반올림·배분 결과를 사용한다. 목표의 잔여 현금을 임의로 재배분하지 않는다.
- 역변동성은 기존 30% 상한·반올림을 그대로 적용한다. 상한으로 남은 비중을 강제로 재정규화하지 않는다.

이 차이를 수정하려면 추천과 시뮬레이션을 함께 바꾸는 별도 전략 버전이 필요하다.

## 3. 공통 시작일과 결정 일정

12개월 팩터는 **T에서 N개월 전 달의 말일 이하 마지막 승인 종가**를 참조한다.
실제 [frame 생성](../../../crates/factor-engine/src/bars.rs)은
`month_end(months_back(T, N))`을 사용하고 탐색 범위를 T까지로 제한한다.
`return_12m = close(T)/close(ref12m)-1`,
`momentum_12_1 = close(ref1m)/close(ref12m)-1`이다.
252개 세션 전 가격이나 T와 같은 일자의 전년 가격으로 대체하지 않는다.
50/200 추세는 T를 포함한 200개 종가, 60일 변동성은 60개의 수익률을 위한 61개 종가가 필요하다.

권장 시작일 S는 다음을 모두 만족하는 T의 다음 승인 세션 중 가장 이른 날이다.

1. T까지의 승인 prefix만으로 모든 기본 전략의 팩터 참조와 계산이 성립한다.
2. 11종목의 필수 팩터 값이 모두 존재하고 유한하며, 역변동성의 변동성은 양수다.
3. 모든 target snapshot과 기존 input/factor/target identity 검증이 통과한다.
4. S가 존재하고 S부터 종료일 E까지 S를 포함한 평가 세션이 적어도 두 개다.

실제 준비 세션 수·최초 신호일·평가 시작일을 결과에 기록한다. 200 또는 252를 모든 전략의
고정 준비 기간으로 재사용하지 않는다. 이 권장안은 승인 입력을 사용하는
[Owner-beta 계산 경로](../../../crates/job-queue/src/owner_beta/compute.rs)의 실제 팩터 준비를 따른다.
일반 추천 경로의 별도 `N prior sessions` 검사를 추가로 적용하지 않는다.
시작일 선택은 참조 가능성만 검사하며 수익률을 보고 고르지 않는다.
기본 종료일은 같은 승인 입력의 마지막 세션이다. 사용자가 기간을 좁힐 경우에도 모든 전략에 같은
S/E를 적용하고 준비 부족은 거절한다. 개별 전략별 최장 기간 결과를 혼합 비교하지 않는다.

최초 S 시가는 prev(S) 종가 신호로 모든 전략을 초기화한다. 월말 전략도 첫 진입은 이 공통일에 한다.
이후 월말 신호일 T는 **다음 승인 세션이 존재하며 연·월이 바뀌는 세션**이다. 다음 세션 시가에
순수량 차이만 재조정한다. 월말 목표가 직전과 같아도 가격 변동으로 생긴 비중 차이는 재조정 대상이다.
월 중간에는 수량과 마지막 결정의 target identity를 유지한다.
승인 범위 끝이라는 이유만으로 그 날을 월말로 간주하지 않는다.

시작 뒤 각 신호 결정일에도 해당 전략의 필수 팩터 전체를 검사한다. NULL·비유한 값이나
역변동성의 0 이하 값은 전체 pair 실패이며, 일부 종목을 제외해 계산을 계속하지 않는다.
이는 기존 target 함수의 부분 NULL 제외 동작에 도달하기 전에 적용할 v2 입력 경계다.

추세 전략은 목표가 계속 100%면 잔여 현금을 추가 매수하지 않는다. 매수 후 보유와 벤치마크도 같다.
최종일은 종가 평가로 끝내며 미래 신호·범위 밖 체결·강제 청산을 생성하지 않는다.
월말 판정에 쓰는 세션 달력과 신호 입력 prefix를 구별하고, 미래 가격은 팩터에 전달하지 않는다.

## 4. 여러 종목의 정수 주 원장

다음은 v1에 없던 **새 권장 수량 규칙**이다. 계산은 checked 정수·정확 분수로 수행한다.
가격·금액은 0.0001원 단위 정수, 비중은 합계 1,000,000인 기존 ppm 값을 쓴다.

재조정 시가 직전 현금 C, 기존 수량 q_i, 시가 p_i, 목표 비중 w_i와 현금 비중 w_cash에 대해:

1. 비용 전 시가 NAV `V = C + Σ(q_i × p_i)`를 한 번 고정한다.
2. 종목별 목표 수량 `q*_i = floor(V × w_i / (1,000,000 × p_i))`를 계산한다.
3. `q_i > q*_i`인 초과 수량만 종목 ID 오름차순으로 매도한다. 매도 비용을 즉시 차감한다.
4. 매도 후 현금 C' 중 `R = min(C', floor(V × w_cash / 1,000,000))`를 남겨둘 현금으로 잡는다.
   매수 가능 예산은 `B = C' − R`이다. 목표 비중은 비용 전 목표이며, 비용 때문에 현금 목표와
   실제 현금이 달라질 수 있다.
5. 부족 수량 `b_i = max(0, q*_i − q_i)`의 원금과 해당 매수 비용을 합친 필요 예산 D_i를 구한다.
   D_i 합이 B 이하이면 그 부족 수량을 전부 산다.
6. 합이 B를 넘으면 각 종목 예산을 `floor(B × D_i / ΣD_i)`로 줄인다. 각 예산으로 원금과 비용을
   감당할 수 있는 최대 정수 주를 사되 b_i를 넘지 않는다. 비용 0인 경우도 같은 절차다.
7. 종목별 예산 반올림과 정수 주 제약으로 남은 돈은 현금으로 보존한다. 잔액으로 특정 종목을
   추가 매수하는 두 번째 배분은 하지 않는다. 체결 기록의 순서는 종목 ID 오름차순이다.

매도와 매수는 같은 원래 목표 수량을 따른다. 비용을 빼고 목표를 다시 계산하는 반복이나
매도한 종목의 같은 재조정 내 재매수는 없다. 한 종목·방향·세션의 수량은 한 주문으로 합쳐
비용 올림을 한 번 적용한다. 수량 0은 체결이 아니며 비용도 없다.
실제 체결 수량이 양수인데 해당 세션 거래량이 0이면 전체 pair를 거절한다.
거래량이 양수이면 위 시가에 전량 체결됐다고 가정하며 유동성·부분 체결 모형을 추가하지 않는다.
음수 현금·수량, 오버플로, 불일치한 NAV/비용/포지션은 두 비용 결과 전체를 실패시킨다.
q=0인 매수는 수량 부족으로 기록하고 해당 전략의 다음 정상 재조정 때까지 재시도하지 않는다.

역변동성 30% 상한은 신호의 목표 비중에 적용한다. 비용·정수 주·가격 변동 뒤 실제 평가 비중을
항상 30% 이하로 보장하는 별도 제한은 아니다. 결과에는 목표와 실제 비중을 구별해 표시한다.

이 방식은 구현과 재현이 단순하지만, 정수 주가 비싼 종목에서는 현금이 비교적 많이 남을 수 있다.
잔액을 다른 종목으로 재배분하는 방식은 실제 비중·비용·성과가 달라지는 별도 선택지다.

### 작은 수작업 기준값

다음은 실제 ETF 성과가 아닌 합성 산술 예다. 초기자금 1,000원, A 시가 100원, B 시가 50원,
목표 A/B 각각 50%를 사용한다. 위 규칙을 Python 정수 산술로 별도 대조했다.

| 상황 | 매도 | 매수 | 종료 수량 A/B | 잔여 현금 | 당일 비용 |
| --- | --- | --- | --- | --- | --- |
| 첫 진입, 0비용 | 없음 | A 5주/B 10주 | 5/10 | 0.0000 | 0.0000 |
| 첫 진입, 각 방향 10bp | 없음 | A 4주/B 9주 | 4/9 | 149.1500 | 0.8500 |
| A 10주·현금 0에서 B 100%로 전환, 10bp | A 10주 | B 19주 | 0/19 | 48.0500 | 1.9500 |
| 첫 10bp 진입 뒤 A=150/B=50이 된 월말, 같은 50/50 목표 | A 1주 | B 2주 | 3/11 | 198.9000 | 0.2500 |

마지막 행의 체결 전 NAV는 1,199.1500원, 체결 후 NAV는 1,198.9000원이다.
그 가격 변동이 월중에 일어나면 월말 전에는 체결하지 않는다.
산술 대조는 제안의 수치 일관성 확인이며 Rust 엔진·실제 입력 검증을 대체하지 않는다.

## 5. 결과·지표·호환성

전략마다 두 비용 프로필 결과를 하나의 원자적 pair로 저장하는 경계는 유지한다.
다섯 전략 전체를 한 트랜잭션으로 묶거나 일부 전략의 성공을 다른 전략의 성공으로 표시하지 않는다.
각 pair는 전략 snapshot, 계약 v2, input pins, 실제 팩터 정의/소스 identity, 엔진 identity,
공통 기간, 결정 일정, 일별 포지션·현금·체결·비용과 기존 허용 지표를 canonical hash로 묶는다.
사용자 ID·실행 ID·시계 시각을 계산 해시에 넣지 않는 기존 원칙은 유지한다.

종가 NAV는 `현금 + Σ(보유수량 × raw close)`다. 회전율 분자는 모든 종목의 매수·매도 원금 합,
분모는 해당일 비용 전 시가 NAV의 두 배다. MDD·수익률·비용·체결 수는 원장에서 다시 검증한다.
벤치마크는 같은 S/E와 비용 프로필의 069500 최초 매수 후 보유다. `buy_and_hold` 기본 전략과
벤치마크의 경제적 원장은 같아야 하지만 전략 identity 때문에 결과 전체 해시가 같을 필요는 없다.

v1 JSON과 DB 결과는 v1 검증기로 계속 읽는다. v2는 새 schema/계약 identity로 구분하고
알 수 없는 버전은 거절한다. 기존 migration0063·인증 전달물·R4-05 실패/성공 증거를 수정하지 않는다.
요청·job·runner·저장·조회가 같은 전략과 버전을 검증하도록 연결한다. 이전 전략 설정의 이름만
바꿔서 다른 전략 결과를 반환하거나 일반 Nautilus 결과를 전용 성과로 보여주지 않는다.

API는 기존 전용 경로와 한 요청당 한 전략이라는 단위를 유지한다. v2 생성에는 명시적인
계약 선택을 추가하고, 선택 필드가 없는 기존 요청은 v1 의미를 유지한다. 클라이언트가 비용·입력 pin·
owner·engine을 임의로 지정하지 않으며, 서버가 해당 사용자의 활성 설정을 고정 기본값과 대조한다.
기존 설정 저장 절차를 사용하고 다섯 설정을 몰래 생성하지 않는다. v2의 idempotency namespace와
의도 비교에는 계약·전략 snapshot을 묶는다. 목록·재조회·취소·재사용도 저장된 버전으로 dispatch하며,
현재 바이너리의 v2 상수를 과거 v1 행에 붙이지 않는다.

새 forward migration은 v1 이력이 있는 상태의 upgrade를 지원해야 한다. v2 이력이 있으면
구버전 제약으로 되돌리는 downgrade를 명시적으로 거절하고, 데이터를 지워 rollback을 통과시키지 않는다.
재조회는 저장된 두 원본 canonical body와 hash를 그대로 검증한다. 수학적 내용이 같더라도 소유권과
FORCE RLS·완료 상태·두 프로필의 완전성 검사는 사용자별로 유지한다.

화면에는 전략·평가 기간·초기자금·가정 비용·현금 잔여·가격수익률/PIT 한계를 함께 표시한다.
모든 비교 행의 기간·비용 프로필·v2 계약·입력 pin·엔진 identity가 같아야 한다.
v1 결과는 기존 기간·버전대로 별도 표시한다.

## 6. 구현과 검증 순서

아래는 코드 점검 후 구체화할 작업 분할이다. 새 계산 규칙 결정 전에는 제품 소스를 바꾸지 않는다.

1. **계약·원장:** v2 닫힌 결과 타입, 다종목 포지션/체결, 위 산술 fixture와 금액/수량/overflow 불변식.
2. **입력·신호:** 기존 추천 팩터/target 재사용, 공통 준비 기간과 월말 일정, 미래 가격 변경 회귀,
   동률·목표 반올림·역변동성 상한 보존, 벤치마크·두 비용 프로필.
3. **전용 실행·저장:** 전략/계약 identity의 admission→job→runner→pair→read 연결, v1/v2 호환,
   원자 publication·취소·재시도·권한 회수·다른 사용자 거절 유지. DB 확장은 새 migration으로만 수행.
4. **API·Web:** 다섯 기본 설정 선택과 전략별 결과, 잘못된 버전/설정 거절, 동일 기간 비교, 기존 결과 회귀.
5. **통합 검증:** 독립 소스 리뷰 후 같은 후보의 기존 hosted CI/required·PG·Web·smoke를 모두 수행한다.
   승인 입력 실행이 필요하면 새 후보 전달물과 구체적인 실행·자원·정리 범위를 먼저 고정한다.
6. **출시:** 검증된 후보의 공식 immutable-release 절차, 순차 이미지 빌드·건강/복구 조건,
   실제 Owner 화면 확인을 별도 기록한다. 관리자 권한의 존재만으로 운영 설치·사용 인수를 완료 처리하지 않는다.

현재 [공식 이미지 목록](../../../deploy/build/release-build-layout.json)에는 Daily용 owner-beta runner는
있지만 전용 simulation runner의 recipe/service는 없다. 출시 작업은 그 runner의 공식 이미지·출처 검증,
읽기 전용 입력·권한·상태 확인·정상 종료·복구를 배포 절차와 함께 구현해야 한다. hosted에서 받은
검증용 실행 파일을 임의 운영 데몬으로 실행하지 않는다. 새 금융 계약 버전만을 이유로 기존
`owner-beta-simulation-build-v1` 출처 영수증 schema를 바꾸지는 않는다.
최종 출시의 R1/R2 의존과 R2/R3의 미완료 인수는 별도로 보존한다.

완료 근거는 소스, 합성 산술/회귀, hosted, 승인 입력, 운영 설치, Owner 사용 확인으로 나눠 기록한다.
기존 R4-05의 네 번 실행 한도는 소진된 과거 기록이며 새 실행에 재사용하지 않는다.

## 7. 소스 점검에서 확인한 차이

- [일반 Python 추세 계산](../../../nt/strategies/trend_following/target.py)은 `fast_value > slow_value`를
  사용하지만 승인된 Rust 경로는 `trend_fast < trend_slow`를 사용한다. 같은 팩터 의미에서 방향이
  반대다. 이 확장은 승인된 Rust 계산을 재사용한다. 일반 Python 결과와의 일치나 그 경로의 보정은
  이번 초안의 검증 결과로 주장하지 않는다.
- [return 팩터 파일의 설명](../../../crates/factor-engine/src/factors/returns.rs)은 일자를 제한한
  T−N개월을 언급하지만 실제 frame과 [월 계산 모듈](../../../crates/factor-engine/src/months.rs)은
  위 월말 규칙을 사용한다. v2 구현 시 설명·회귀를 실제 계산과 맞추고 승인된 계산 자체는 바꾸지 않는다.
- 현재 API 조회 DTO는 v1 상수를 반환하고 Web도 추세/단일 종목에 고정돼 있다. 저장된 버전별 검증,
  다섯 전략 표시, 다종목 보유 내역을 함께 바꿔야 한다. 공식 simulation runner 출시 연결도 남아 있다.

## 8. 현재 확인 수준과 결정 요청

계산과 API/출시 경계의 독립 소스 감사 두 건을 회수·통합하고 제안 산술 네 건을 대조했다.
감사 보고서는 `target/r4-expansion-20261026/{engine-audit,surface-audit}/report.md`에 보존한다.
제품 구현, 새 Rust 테스트·hosted 실행, 승인 입력 실행, 운영 설치는 미수행이다.

권장안 대신 전략별 각자 가능한 최장 기간을 쓰거나, 매수 잔액을 다시 배분하거나,
월중에도 비중을 맞추려면 결과가 달라진다. 결정이 필요한 부분은 이 새 규칙이며,
이미 승인·검증한 v1 계약을 다시 승인받는 절차가 아니다.
