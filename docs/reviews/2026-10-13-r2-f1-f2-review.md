## Prioritized actionable findings

### P2 — isolate inherited state/cutoff variables in the fake-host test

Location: `scripts/ops/backfill-production-self-test.sh:250–266` (especially
253–264), with the unbounded fake `stat` results at 133–144.

`env` here adds fixture variables but retains the caller's environment. The
fixture pins the state directory and lock, but does not pin or clear
`KIS_DAILY_STATE_FILE` or `KIS_DAILY_EARLIEST_TODAY_KST`. The real daily script
consumes those overrides (`kis-daily-production.sh:527,562–570`); the dotenv
override checker only considers declared dotenv/security keys, which do not
include these two (`scripts/ops/lib/dotenv.sh:67–120`).

Consequently, an inherited state-file override can select an existing writable
regular file outside the random fixture directory. The fake `stat` certifies
any such path as root-owned/protected; existing files bypass the path-limited
fake `chown`. For an empty file the real state helper appends the fixture V4
header and DB-derived PUBLISHED row before delegation
(`kis-daily-production.sh:295–312,562–595`;
`scripts/ops/lib/kis-daily-state.py:182–196`). Later assertions use the canonical
fixture filename and can fail after that external append. Thus the promised
temporary-state boundary is not guaranteed by the current test source.
An inherited cutoff override also changes the intended 16:29:59/16:30:00 cases.
This is a test-isolation defect, not a demonstrated production write.

Requested fix, confined to the existing self-test: launch fixture commands with
a clean allowlisted environment, pin the daily state filename and default 16:30
cutoff explicitly, and restrict temporary staging to the fixture. Keep the
fake root/ownership claims confined to fixture paths (with the necessary
descriptor handling). Add a hostile-inherited-environment case using an
external **test-owned** sentinel file: it must remain byte-identical while
the canonical fixture state and exact clock-boundary arguments are exercised.
Do not use production paths for that regression. This scenario was not executed
during review; it follows the actual override/write path above.

### P2 — align dynamic scheduler fixture dates with its rights interval

Location: `crates/api-server/tests/owner_equity_v2_db.rs:1093–1100,1134–1164`.

The new regression derives `eligible`, `prior_close` and the initial generation
from the live database clock. Its otherwise valid schedule pins reference the
common harness entitlement, whose fixed interval is 2026-01-01 through
2026-12-31 (`crates/api-server/tests/common/mod.rs:348–353`). The existing SQL
checks `effective_from <= p_as_of <= effective_until` before its active-job
early return (`migrations/0053_owner_managed_equity_universe_v2.up.sql:1135–1183`).
Once the DB's eligible date advances beyond 2026-12-31, the call after the late
calendar insert fails the rights gate instead of returning the expected
zero-work report; once the prior close is outside the interval, the first
valid scheduling call can fail earlier. The test therefore expires with the
wall clock despite using valid reference/hash values. Within the current
2026 interval this finding does not assert an observed failure.

Requested fix: make the disposable QA dates/entitlement fixture consistent
without relaxing production rights checks. Either use explicitly bounded
historical dates compatible with the database eligibility gate, or seed a
dedicated QA entitlement covering the chosen dynamic fixture dates. Keep the
unregistered-rights case separate. Verify both sides of the fixture year
boundary through an isolated test seam; no production clock or policy change
is needed or authorized by this review.

No concrete production-code defect or obvious Rust type/signature error was
found in the reviewed F1/F2 paths. This statement does not mean compilation,
DB behavior or test execution passed. The two findings above should be resolved
or explicitly dispositioned by the coordinator before treating test evidence
as suitable for acceptance.
