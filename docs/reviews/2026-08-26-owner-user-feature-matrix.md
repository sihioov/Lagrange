## Reading the classifications

- `WORKING_EVIDENCE`: the implementation and checked-in automated evidence cover
  the stated behavior, including a meaningful result where the function promises
  one.
- `TEST_GAP`: a user-visible function or recovery path is implemented, but the
  inspected evidence does not cover the complete user action/result contract.
- `EXPECTED_BLOCK`: the product deliberately withholds the function under the
  current beta policy; this is not a defect.
- `USER_ACCEPTANCE_PENDING`: the fixture or contract evidence is useful, but the
  final Owner action or production-only result has not been performed.

“Rendered” below means that HTML or a state panel exists. It is not treated as a
meaningful usable result unless the row says that the required data/result is
also present.

## Core Owner journey and acceptance boundary

The intended beta journey is:

`/login` → authenticated session → `/strategies` → save one active config →
`/recommendations` → create owner-beta run for `as_of=2026-08-19` → poll →
open the persisted report/history entry.

The code, disposable-fixture tests, and status record cover the HTTP/DB/browser-
equivalent ordering, CSRF repair, policy gate, and sealed-result contract. The
production strategy save has now been accepted by the Owner and verified as one
active config. The remaining production step is to use the real Auth0 session,
create one recommendation, and confirm the meaningful report. It must not be
simulated by extracting credentials, cookies, tokens, or by impersonating the
Owner.

The page can therefore be healthy while the final acceptance rows remain pending:
rendering a form, a `202 PENDING`, or a history shell is not proof that durable
configuration or a completed report was produced. Paper and Live being disabled
are policy outcomes, not defects; this matrix makes no performance or readiness
claim for either product.
