## 구현 API와 계약 대응

공개 API는 `simulation::run_approved_historical_price_only_simulation(artifact_root, request,
identity)`다. `SimulationRunRequest`에는 기존 Owner-beta `run_id`/`strategy_config_id`와 선택적
평가 시작·종료 세션을 받는다. 이 ID는 기존 입력을 만드는 데만 쓰며 작업을 enqueue하지 않고 결과
provenance에도 넣지 않는다. 기본 기간은 승인 세션 `d[200]..=d[2451]`이며 준비 세션 200개와 평가
세션 2개 미만, 승인 달력 밖 날짜, 역순은 거절한다.

| 계약 항목 | WP-4 연결 |
| --- | --- |
| P0-01~02 일정·신호 | `ExpectedRangeSessions::approved_xkrx`의 독립 승인 순서를 사용한다. 각 평가 세션 S의 바로 전 승인 세션 T에서 기존 computation을 `as_of=T`로 부르고 S 시가 실행에 연결한다. 마지막 평가 세션에서 그 뒤 신호는 만들지 않는다. |

각 T에서 승인된 같은 artifact object로 `OwnerBetaPriceRecommendationInput`을 만들고, 추출한
`compute_owner_beta_price_recommendation_with_approved` helper를 부른다. helper는 기존 strategy
snapshot, pins, factor requirements/versions, `PriceOnlyFactorSnapshotBuilder`, factor hash,
target builder/hash/identity 검사를 유지한다. 실제 factor 계산은 전용 SMA 구현을 만들지 않고
`trend_50`/`trend_200` 및 기존 `build_target_snapshot`만 사용한다. 기존 target 규칙의
`trend_50 < trend_200` 조건이 아니면 cash를 유지한다.

`SimulationRunIdentity`는 `EngineIdentity`와 필수 `factor_definition_sha256`을 받으며 기본값은
없다. `EngineIdentity` 필드는 문법만 검사한다. 최종 격리 빌드의 revision, 실제 executable SHA-256,
toolchain/target/profile을 private receipt로 연결하기 전에는 실행 provenance가 아니다.

## 테스트와 검사

작성한 synthetic 회귀는 200일 warm-up 경계, 날짜 창/역순, 세션×ETF11 누락·중복·추가, OHLC 조정
차이, 0 이하 가격, 승인 metadata labels/non-cash action, cash/full-weight target mapping,
결정적 결과 hash, profile 쌍 불일치 거절, 5개 승인 pin 변조 거절과 artifact 부재 거절이다. 테스트는
sealed 승인 artifact를 만들거나 승인 경계를 우회하지 않는다. 기존 owner-beta input 검사에는 strategy
snapshot tamper 회귀가 있고, target builder는 50/200 factor 비교를 그대로 사용한다.

실행한 확인:

- `python3 scripts/qa/dev-check.py plan --base HEAD --format json` — PASS, read-only plan. 공유 `Cargo.lock`
  변경 때문에 전체 hosted integration plan이 표시됐으며 integration은 실행하지 않았다.
- `python3 scripts/qa/dev-check.py preflight --profile rust --stage fast` — PASS.
- `python3 scripts/qa/dev-check.py preflight --profile docs --stage fast` — PASS.
- `python3 scripts/qa/dev-check.py run --profile rust --stage fast` — 최종 PASS (receipt는 private WP-4
  receipt에 기록). 첫 시도는 새 파일의 rustfmt 차이를 찾아 보정 후 재실행했다.
- `python3 scripts/qa/dev-check.py run --profile docs --stage fast` — PASS (receipt는 private WP-4

요청된 리소스 경계에 따라 Rust compile, unit/integration tests, Clippy, 실제 승인 artifact 실행,
실제 executable provenance는 `NOT_RUN`이다. 로컬 승인 artifact root는 확립되지 않았으며 이를 찾거나
복사·재수집하지 않았다. 기존 focused preflight 차단 조건을 우회하지 않았다.

## 미해결 경계

현재 factor engine은 `trend_50`과 `trend_200` 각각의 version을 snapshot map에 저장하지만, 두 정의를
묶는 canonical factor-definition identity 또는 SHA-256 producer는 없다. R4 result schema의 단일
`factor_definition.version`/`sha256`를 만들 기존 authoritative representation도 찾지 못했다.
구현은 같은 실제 factor version이 두 항목에서 확인될 때 그 version을 사용하고, SHA-256은 호출자가
명시적으로 제공하게 했으며 snapshot hash나 임의 기본값으로 대체하지 않았다. 이 raw digest 인자는
검증된 provenance가 아니다. 실제 결과를 인정하려면 factor-definition digest의 authoritative source와
기존 두 factor를 하나의 identity로 표현하는 결정을 확정해야 한다.

승인 artifact가 없으므로 full pipeline future-price perturbation 테스트와 실제 signal/target equality
검사는 실행할 수 없었다. factor-engine의 기존 `later_rows_do_not_change_an_earlier_snapshot_or_hash`
unit test와 as-of 필터 경계는 source로 확인했지만 이번 변경의 실행 증거로 승격하지 않는다. 추가로,
동률 입력에서 target builder가 cash를 내는 full sealed-input 회귀도 실행되지 않았다. WP-4의 synthetic
signal mapping은 이미 만들어진 cash target을 그대로 매핑하는 것만 검증한다.

이 보고서는 소스 구현 및 허용된 fast formatter/whitespace 검사만 기록한다. G4 후보 수용, hosted 검사,
실제 데이터 성과, 배포 또는 Owner acceptance를 주장하지 않는다.

## WP-4 보완 — 기존 정의 identity와 합성 회귀

앞 절의 factor-definition identity 공백과 합성 회귀 공백은 최초 WP-4 검토 당시의 기록이다. 후속
고정 보완 범위에 따라 호출자 제공 `factor_definition_sha256`을 제거하고 `SimulationRunIdentity`는
engine identity만 받도록 바꿨다. 전략 identity의 factor definition은 고정 50/200 전략의 기존
`requirements_for`와 `factors_for` 결과에서 내부 생성한다.

descriptor는 ASCII ID 순서로 `trend_200`, `trend_50`을 담고 실제 `Factor`의 version,
`required_fields`, `lookback`, `null_policy`를 읽는다. 정확히 `CLOSE`, 각 200/50 trading-day full
window, `InsufficientLookback`, 두 버전 일치 조건을 검사한다. SHA-256은 기존 canonical JSON helper로
계산하며, factor contract / TrendFactor 구현 / `lazy_util.rs`의 compile-time 포함 바이트 digest를
descriptor에 연결한다. 각 as-of factor snapshot의 version map도 이 두 구현 값과 정확히 같아야 한다.
이 descriptor hash는 U3 executable provenance를 대신하지 않는다.

합성 회귀는 기존 승인 우회 없는 test-only seams를 사용한다. factor-engine 테스트는 230개 ETF11
평일 세션으로 실제 `TrendFactor::new(50)`과 `new(200)`을 계산하고, 200개 과거 관측을 가진 T 뒤의
raw/adjusted 가격만 바꿔 T의 non-null 수치 행과 version map이 유지되는지 비교한다. test-only pins는
서로 다르게 두어 전체 lineage hash가 같다고 주장하지 않는다. owner-beta target 테스트는 기존
`build_target_snapshot`으로 benchmark `069500.KRX`, fast 50/slow 200에서 동률→현금, fast<slow→매수,
fast>slow→현금을 만들고 hash를 검증한다. 같은 동률 factor 행을 재구성했을 때 target hash도 같다.

새 회귀는 소스에 추가했으며 실행하지 않았다. Cargo compile/unit/integration/Clippy는 최종 hosted
검증 전 `NOT_RUN`이다. 실제 승인 artifact end-to-end, U2 artifact root, U3 executable provenance도
계속 `NOT_RUN`이며, 초기 소스 검토의 “실제 artifact 없음” 경계는 그대로 적용된다.
