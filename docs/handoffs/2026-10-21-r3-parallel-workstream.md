# R3 병행 작업 인계

## Owner 결정과 담당

2026-10-21 Owner는 “일단 R2는 R2대로 진행하고 R3는 다른 쪽에서 이어서 진행하면
안되나?”라고 지시했다. R2 완료를 기다리지 않고 별도 작업공간에서 R3를 병행한다.
R2-01~09, 실제 Owner 사용과 연속 3거래일 기준은 그대로 유지한다. R3의 실제 수신과
최종 인수도 별도로 판정한다. 병행 착수는 어느 단계의 완료 증거도 아니다.

- R2: 기존 `excited-dolphin`의 같은 에이전트가 계속 담당한다. R2 위임 금지는 유지한다.
- R3: 별도 브랜치·작업공간의 담당 에이전트가 R3-01~07을 추적한다.
- 이번 병행 결정은 계좌·주문·실거래·추가 공급자 권한을 늘리지 않는다.
- 작업공간 생성·담당 실행의 실제 영수증은 R2 작업공간의
  `target/r2-daily-beta/owned-workers.json`의 `parallelWorkstreams.r3`에서 찾는다.
  이 파일의 계획만으로 에이전트가 실행 중이라고 주장하지 않는다.

## 고정된 출발점과 사실의 시점

분기 전 문서 HEAD는 `1c53a1ad884a58075fbef1a661927a47dcd7bc79`다. R3는 이 결정이
포함된 문서 커밋에서 분기한다. 저장소 `main`은 별도 개발 흐름이며 임의로 합치지 않는다.
이 문서와 그 후속 문서 커밋은 R2의 이미지 빌드 후보가 아니다.

- R2 소스 후보 `fccb68354c5352f741c37764ae1d66eb3784a662`: CI 39457995014
  attempt 1의 8개 job 성공과 전체 로그 인수 완료. 새 이미지·배포는 미실행이다.
- 마지막으로 인수된 실제 앱은 `e639169018519fd6636c5579d1957e323e2c7802`, schema 62다.
  G4, 공식 정기 백업 전환과 실제 암호화 백업·격리 복원은 완료된 증거를 보존한다.
- 2026-10-20 실제 관측에서 일일 추천 OFF/epoch 0, KIS daily timer disabled였다.
  실제 새 일일 입력 인수·자동 실행·Owner 사용·연속 3거래일은 미완료다.
- R2 a2는 2026-10-20 17:01:50 UTC에 `sudo: interactive authentication is required`로
  root Python 실행 전에 종료됐다. 재실행하지 않는다. 마지막 scoped host 관측은
  17:03:00.525235 UTC이며, 이후 이 문서 작성은 새 운영 관측이 아니다.
- R2 시작일은 실제 배포 검증 뒤 첫 실제 거래일이다. 조건부 10월 21일 후보는 기한이
  지나 소진됐고 대체 날짜는 미정이다. R3가 날짜나 R2 성공일을 대신 만들어서는 안 된다.

R2의 최신 상태는 위 registry의 `coordinatorTask.boundedHandoff`를 읽고 기록된
SHA-256을 대조해 확인한다. R3는 이 registry와 R2 증거 파일을 수정하지 않는다.

## R3의 첫 실행 범위

R3-01의 소스·계약 대조와 R3-06의 공개 공식 문서 확인부터 실제로 진행한다. 현재 구현을
파일·행·커밋으로 연결하고, 이미 인수된 소스·합성 검사·역사 설치·실제 수신을 구분한다.
공식 공개 자료를 조회할 때 현재 확인일·URL·개정·접근 실패를 기록하고, 비공개 문서나
키 사용량을 추측하지 않는다. 공개 문서 조회는 승인키 발급이나 시장 연결이 아니다.

첫 산출물은 `docs/reviews/2026-10-21-r3-parallel-readiness.md`다. 다음을 포함한다.

- R3-01~07 각각의 완료된 근거, 남은 차이, 다음 실행과 필요한 운영 의존성.
- 정상 Owner 수요·READY 1종목 pilot에서 실제 ACK/47필드/새 수신/해제·종료를 확인하는
  정확한 순서와 증거 항목. 이어 인증 화면·수명주기와 30종목 인수를 구분한다.
- 기존 코드의 결함인지, 새 운영 관측이 필요한 것인지 구분한 구체적인 후속 작업.
- R2와 겹치는 서비스·DB·달력·credential slot·설치 도구·릴리스 변경 지점.
- 확인하지 못한 사실과 이유. 역사적 health나 fixture를 실제 수신으로 대체하지 않는다.

첫 대조에서는 소스 읽기·공개 공식 문서 조회와 문서 작성만 수행한다. 새 결함을 찾으면
독립적으로 수정할 수 있는 범위를 명확히 보고한다. 이미 통과한 R2 검사/CI를 반복하지 않는다.
R3 작업공간 안에서 R3 상태·다음 작업·변경 이력을 갱신하며, R2 완료 체크를 바꾸지 않는다.
첫 대조 종료 후에는 후속 범위와 운영 의존성을 보고해 실제 다음 작업으로 연결한다.

## 병행 실행의 운영 경계

별도 Git worktree도 같은 운영 호스트 자원을 공유할 수 있다. 첫 대조 중에는 sudo 재시도,
Docker/Compose/systemd 변경, 운영 DB 조회·쓰기, provider 인증·시장 연결, 무거운 빌드나
테스트 프로세스를 시작하지 않는다. 비밀 파일·dotenv·세션 쿠키를 읽거나 복사하지 않는다.
프로젝트 setup script, timer, 별도 heartbeat를 임의 실행하지 않는다. 추가 에이전트도 생성하지 않는다.

실제 운영 작업 전에는 R3가 대상·목적·정확한 변경·복구 경로·요청 예산을 정리하고 R2 담당과
실행 시간을 조율한다. 이것은 확보된 Owner 승인을 다시 묻는 절차가 아니라 공유 운영 자원의
직렬화다. R2 빌드·배포·복원과 동시에 같은 서비스를 변경하지 않는다. R2 관찰 대상 릴리스나
입력·실행 동작에 영향을 주는 변경은 3거래일 관찰의 재시작 조건과 대조한다.

기존 ADR-0009 한계인 시장 연결 1개·H0STCNT0 최대 30등록, 정상 membership/READY/Owner
수요, 당일 달력·장 시간 증거, 기존 실패 예산을 유지한다. 용량·다른 기기의 같은 키 사용이
미확인인 사실은 미확인으로 남긴다. 추가 연결이나 임의 승인키 재발급으로 탐색하지 않는다.
실시간 REST fallback·계좌·주문·Member 전달·재배포는 범위 밖이다.

R2 release lock, PG 권한, 역사 failed/disabled unit과 research exit2, 원인 미확정 기록 및
소유권 미확정 volume `159b052fed63a476fba2c51c8f15f532a837096e4bdd453bb753789672034f07`은
그대로 보존한다. mount/content/delete/prune이나 전체 chmod/chown을 수행하지 않는다.

## 보고 형식과 완료 판정

변경 파일·행, 근거 커밋, 검증 방법/실행 여부, 미해결 항목, 확인하지 못한 사실과 다음 범위를
짧게 보고한다. 문서 준비 완료를 R3-01의 실제 설치 검증 완료로 표시하지 않는다.
`SOURCE_LOCAL_ACCEPTED`, 설치 상태, 실제 연결·수신, `LIVE_ACCEPTED`, `FINAL_ACCEPTED`는
각각의 증거로만 판정한다. R2와 R3는 병행하지만 최종 인수 증거를 서로 대체하지 않는다.
